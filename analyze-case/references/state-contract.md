# Контракт состояния

Шаги конвейера не разговаривают друг с другом напрямую. Они пишут и читают **один файл состояния**:

```
/Users/mihail_tarasov/Codex/ePeople/Support/cases/<YYYY-MM-DD>-<слаг>/state.md
```

Это единственный канал передачи. Шаг, который что-то узнал и не записал в `state.md`, считай, не узнал ничего.

## Заголовок состояния

Первым блоком файла идёт YAML. Оркестратор читает **только его** и по нему решает, что запускать дальше.

```yaml
---
case_id: 2026-07-28-scheduled-time-anomaly
created: 2026-07-28
iteration: 1
status: NEEDS_EVIDENCE
scope: auto
scope_resolved: null
depth: fast
depth_escalated_from: null
route: null
verdict: null
secondary: null
confidence: null
return_reason: null
visited: []
---
```

### Поля

| Поле | Значения | Кто пишет |
|---|---|---|
| `status` | `NEEDS_INTAKE`, `NEEDS_EVIDENCE`, `NEEDS_TRIAGE`, `ROUTED`, `RETURN_TO_TRIAGE`, `READY_FOR_OUTPUT`, `DONE`, `BLOCKED` | каждый шаг после себя |
| `scope` | `auto`, `epeople`, `schedule`, `cross` — как запросил пользователь | шаг 01, дальше не меняется |
| `scope_resolved` | какие системы фактически открывались: `[epeople]`, `[schedule]`, `[epeople, schedule]` | шаг 02 и ветки, дописывают по факту |
| `depth` | `fast`, `deep` | шаг 01, повышается любым шагом при эскалации |
| `depth_escalated_from` | `fast`, если глубину повысили по ходу, иначе `null` | шаг, выполнивший эскалацию |
| `route` | `USER_ERROR`, `DEFECT`, `NORMAL_BEHAVIOR`, `INSUFFICIENT_DATA` | только шаг 03 |
| `verdict` | итоговый вердикт | шаг 03, подтверждается ветками |
| `secondary` | `DEFECT`, `UX_DEFECT`, `PRODUCT_GAP`, `null` | ветки 04a/04b |
| `confidence` | `high`, `medium`, `low` | шаг 03 |
| `return_reason` | одна фраза, почему ветка вернула кейс | ветки 04a/04b |
| `visited` | список уже пройденных веток, например `[USER_ERROR]` | оркестратор |
| `iteration` | счётчик проходов через триаж, стартует с 1 | шаг 03 |

### Правила по флагам

**`scope` фиксируется на шаге 01 и не переписывается.** То, что открывали фактически, копится в `scope_resolved` — по нему видно, сработало ли правило перехода. Расхождение `scope: epeople` и `scope_resolved: [epeople, schedule]` означает нарушение жёсткой рамки, и это ошибка разбора.

**`depth` повышается только в одну сторону.** Любой шаг, наткнувшийся на условие эскалации из `SKILL.md`, ставит `depth: deep` и записывает в `depth_escalated_from` прежнее значение. Понижение запрещено: кейс, однажды признанный требующим глубины, её не теряет.

**При `depth: fast` петля пересмотра отключена.** Ветка, обнаружившая неверный маршрут, не ставит `RETURN_TO_TRIAGE`, а вместо этого повышает `depth` до `deep` и только потом возвращает кейс. Так возврат случается один раз, а не по кругу.

## Разделы файла

Каждый шаг владеет своим разделом и **дописывает**, не переписывая чужое.

```markdown
## 1. Кейс          ← пишет 01-intake
## 2. Эталон        ← пишет 02-evidence
## 3. Доказательства ← пишет 02-evidence, дополняют ветки
## 4. Журнал триажа  ← пишет 03-triage, по записи на каждую итерацию
## 5. Разбор ветки   ← пишет 04a или 04b
## 6. Отброшено      ← пишет любой шаг
## 7. Пробелы        ← пишет любой шаг
```

## Правила цикла

Ветка, обнаружившая, что маршрут был неверным, **не переключается сама**. Она возвращает кейс в триаж:

1. Дописывает найденное в раздел «3. Доказательства».
2. Ставит `status: RETURN_TO_TRIAGE` и заполняет `return_reason`.
3. Останавливается.

Триаж при получении возврата:

1. Увеличивает `iteration`.
2. **Не назначает ветку из `visited` повторно, если в разделе доказательств не появилось новых фактов.** Иначе цикл зациклится.
3. При `iteration > 3` ставит `status: BLOCKED` и передаёт человеку. Три круга без сходимости означают, что не хватает данных, а не что нужен четвёртый круг.

## Двойной исход

Вердикты не исключают друг друга. Частый случай: человек ошибся, **и** продукт этому не помешал.

Пример: сотрудника завели вторым аккаунтом. Первичный вердикт `USER_ERROR`. Но если в продукте нет проверки на дубликат, это `secondary: PRODUCT_GAP`, и на выходе создаются **оба** документа — ответ человеку и тикет разработке.

Ветка, поставившая `secondary`, обязана обосновать его доказательством наравне с основным вердиктом. Догадка в `secondary` не допускается.
