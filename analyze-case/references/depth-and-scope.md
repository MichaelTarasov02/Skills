# Глубина и охват

Что именно меняют флаги `--depth` и `--scope` на каждой стадии. Дефолты и правила эскалации — в `SKILL.md`.

---

## `--depth` по стадиям

| Стадия | `fast` | `deep` |
|---|---|---|
| 01 Intake | Как обычно. Приём кейса не сокращается — он дешёвый, а потеря идентификатора дорогая | Как обычно |
| 02 Evidence | `domain-facts.md` целиком, база по объектам кейса, код по найденному механизму. Логи — только если база не объяснила | Всё то же **плюс**: история изменений (`bb_historicalassociate*`), соседние объекты того же человека для сравнения, логи всегда, две точки отсчёта при измерении задержек |
| 03 Triage | Оба вопроса триажа задаются всегда | Так же |
| 04a User error | Позитивное доказательство обязательно | Так же плюс частота состояния на проде числом |
| 04b Defect | **Регрессия и масштаб обязательны и здесь** — см. ниже | Плюс корреляция «до/после» деплоя, проверка контрагента, отдельный подсчёт похожего-но-недоказанного |
| 04c Prevention | Одно предложение вместо трёх | До трёх предложений, каждое с измеренной долей закрываемых случаев |
| 05 Output | Все документы по вердикту. Формат не сокращается | Так же |
| 06 QA | **Обязательна.** Минимум три встречных вопроса | Обязательна |
| Петля пересмотра | Отключена. Ветка не возвращает кейс в триаж, а фиксирует расхождение и эскалирует глубину | Включена, до трёх итераций |

### Чего `fast` не делает

- Не строит таблицу «до и после» даты коммита.
- Не считает частоту состояния по всей базе, если затронут один человек.
- Не открывает вторую систему без правила перехода.
- Не проверяет соседние объекты для сравнения, если объект кейса объяснён.

### Чего `fast` не имеет права не делать

- Читать `domain-facts.md` целиком.
- Задавать оба вопроса триажа раздельно.
- Ставить позитивное доказательство под `USER_ERROR`.
- Проходить стадию 06.
- Искать регрессию и масштаб, **если вердикт — `ДЕФЕКТ`**. На этом пороге `fast` кончается: см. эскалацию в `SKILL.md`. Дефект без даты появления и числа затронутых объектов — это не диагноз, а догадка.

## `--scope` и источники данных

| Значение | База ePeople `whereami_bb` | База Schedule `portal` | Логи ePeople | Код |
|---|---|---|---|---|
| `epeople` | да | **нет** | да | ePeople |
| `schedule` | только для сопоставления идентификаторов | да | да | ePeople в части приёма событий |
| `cross` | да | да | да | обе стороны интеграции |
| `auto` | по правилу перехода | по правилу перехода | да | по правилу перехода |

Обе базы — на одном сервере, отличается имя базы. Команды и схемы — в `environment.md`.

### Сопоставление объекта между системами

Единственная надёжная связка — `whereami_id` в Schedule против `bb_associate.id` в ePeople. Дополнительно `employee_number` против `associate_number`.

```sql
-- ePeople → Schedule
SELECT em.id, em.employee_number, em.start_date, em.end_date, em.whereami_id
FROM sfhcr.schedule_employment em WHERE em.whereami_id = '<associate_id>';
```

**Проверяй оба тенанта.** `sfhcr` и `sfhcr2` замаплены на один и тот же project 1 (`bb_projectexternalservice`, записи 100 и 101). Объект, найденный только в одном тенанте, — половина картины.

### Аудит Schedule

У Schedule стоит Hibernate Envers: у таблиц есть парные `*_aud`, ревизии — в `userrevisionentity` того же тенанта.

```sql
SELECT a.*, to_char(to_timestamp(r.timestamp/1000) AT TIME ZONE 'America/Los_Angeles','MM-DD HH24:MI:SS') AS when_pt,
       coalesce(r.email, '(автор не записан)') AS who
FROM sfhcr2.schedule_employment_aud a
LEFT JOIN sfhcr2.userrevisionentity r ON r.id = a.rev
WHERE a.id = <employment_id> ORDER BY r.timestamp;
```

`revtype`: `0` — создание, `1` — изменение, `2` — удаление.

**Одна ревизия = одна транзакция.** Чтобы понять, что за операция была, посмотри **все** `*_aud` таблицы схемы с этой `rev` — состав транзакции говорит о смысле операции больше, чем одно изменённое поле. Так удаление учётки отличается от увольнения.

**Автор в аудите есть не всегда**, и это не признак автоматики. Прежде чем писать «сделала система», проверь, у какой доли таких же операций автор записан: если у большинства не записан, по аудиту исполнителя определить нельзя, и так и надо сказать.

## Взаимодействие флагов

`--scope=cross` не повышает глубину, а `--depth=deep` не расширяет охват. Флаги независимы.

Осмысленные сочетания:

| Вызов | Когда |
|---|---|
| дефолт | «почему у этого человека вот так» — большинство обращений |
| `--depth=deep` | тикет разработке, инцидент, «нужен исчерпывающий ответ» |
| `--scope=cross` | расхождение между продуктами, спор о том, чья сторона виновата |
| `--scope=cross --depth=deep` | эскалация к команде контрагента, разбор контракта интеграции |
| `--scope=schedule` | «что у них лежит по этому сотруднику» без разбора нашей логики |
| `--scope=epeople` | контрагент уже подтвердил свою сторону, ищем только у себя |
