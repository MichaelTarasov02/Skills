# Методология: структура промпта внутри скилла

Как устроен сам промпт — порядок блоков, примеры, поведение при сбое. Источник: Anthropic
Building Effective Agents и Prompting best practices.

**Рычаги качества текста живут в `../../references/writing-craft.md`** — лестница,
указатели, критерии завершения, ведущие слова, позитивные формулировки, прунинг. Этот файл
их не повторяет: сюда приходят, когда вопрос про **структуру** промпта, а не про его
формулировки.

## Прогрессивное усложнение — начни с простого

Усложняй промпт только после того, как простой провалился. Уровни:

1. Прямая инструкция.
2. + ограничения (объём, формат, границы).
3. + рассуждение по шагам (chain-of-thought), где задача аналитическая.
4. + примеры (few-shot), когда нужен стабильный формат или разбор крайних случаев.

Каждый следующий уровень добавляй, только если предыдущий даёт нестабильный результат.
Сложный промпт до того, как пробовали простой, — самая частая ошибка улучшения.

## Иерархия инструкций

Порядок, который модель читает надёжнее всего:

    [Роль и контекст] → [Задача] → [Примеры] → [Входные данные] → [Формат вывода]

Держи инструкции, контекст и данные разделёнными: в скиллах это делают заголовки и списки,
в API — XML-теги `<instructions>`, `<context>`, `<input>`.

## Показывай, а не рассказывай

Два-три примера «вход → выход» точнее десяти строк описания правил.

Пример обязан совпадать с целевой задачей. Пример из чужого домена уводит модель в тот
домен — это «загрязнение примерами», и оно хуже отсутствия примера.

## Постоянные инструкции, а не одноразовые шаги

Содержимое скилла входит в диалог один раз и заново не читается. Пиши правила как
**стоячие** («всегда делай X»), а не как «сначала сделай X» — иначе поведение рассыпается
на поздних ходах.

## Восстановление после ошибок

Опиши заранее, что делать при сбое: запасной путь, как пометить недостающую информацию,
как сообщить о неуверенности. Пробел в этом месте модель заполнит по-своему, и каждый раз
по-разному.

## Анти-паттерны

| Паттерн | Как выглядит |
|---|---|
| Оверинжиниринг | сложный промпт до того, как пробовали простой |
| Загрязнение примерами | примеры не из целевой задачи |
| Переполнение контекста | избыточные примеры съедают окно |
| Двусмысленность | место для нескольких трактовок |
| Игнор крайних случаев | не проверено на граничных входах |

## Чек-лист правки

- [ ] Диагностирован конкретный симптом (не «давай перепишем»)
- [ ] Взят самый дешёвый уровень усложнения, закрывающий симптом
- [ ] Правка в единственном месте (нет нового дубля)
- [ ] Пройдены пять проверок прунинга из Фазы 3
- [ ] Поведение на старых входах не изменилось
