# Provenance — источники `skill-forge`

Что откуда взято. Нужно, чтобы при обновлении донора было понятно, что чинить здесь.
Формат: `взято дословно` / `переписано под нас` / `отброшено` — с причиной.

---

## 1. `~/.claude/skills/agent-forge/references/skill-spec.md`

Формат скилла, прогрессивное раскрытие, правила `description`.

| Решение | Что именно |
|---|---|
| **Не копировать — ссылаться** | Весь файл. `skill-forge` при работе читает его напрямую. Копия неизбежно разойдётся с оригиналом при обновлении `agent-forge` |
| Взято дословно | Три яруса прогрессивного раскрытия и бюджет тела < 5k слов — как жёсткий числовой критерий в `quality-rules.md` |
| Взято дословно | Правило «информация живёт либо в `SKILL.md`, либо в `references/` — никогда в обоих» |
| Взято дословно | Четыре правила `description`: третье лицо, ключевой кейс первым, слова на языке пользователя, названия артефактов |
| Переписано | Лимит 1536 символов `description` → превращён в проверяемый пункт чек-листа с командой измерения |
| Переписано | «Content lifecycle: файл не перечитывается» → в `quality-rules.md` как требование писать стоячие инструкции; применяется к каждому из восьми собираемых скиллов |
| Отброшено | Таблица мест установки скиллов и precedence — у нас место фиксировано промптами, выбора нет |
| Отброшено | Раздел про симлинки в Codex — вне скоупа Dev Agent |

## 2. `~/.claude/skills/agent-forge/skills/improve/references/prompt-and-kb-methodology.md`

Методология промптов и базы знаний.

| Решение | Что именно |
|---|---|
| Взято дословно | **Заострение критериев** — «каждый шаг заканчивается проверяемым критерием завершения». Это ядро `quality-rules.md` |
| Взято дословно | Тест ветвлением: инлайнить то, что нужно каждому пути; выносить то, что нужно только некоторым. Основа `platform-split.md` |
| Взято дословно | «Указатель контекста решает надёжность»: формулировка «читай X перед фазой N» надёжнее, чем «детали см. в references» |
| Взято дословно | Прунинг: релевантность → no-op-тест по предложениям → осадок |
| Переписано | Прогрессивное усложнение промпта (4 уровня) → применено к собираемым скиллам как правило «не добавляй few-shot, пока прямая инструкция не провалилась» |
| Переписано | Пять анти-паттернов → чек-лист самопроверки в `quality-rules.md` |
| Отброшено | Раздел про XML-теги `<instructions>`/`<context>` — это API-промптинг, в `SKILL.md` роль тегов играют заголовки |

## 3. `~/.claude/skills/agent-forge/references/plugin-spec.md`

Структура плагина — для режима B.

| Решение | Что именно |
|---|---|
| **Не копировать — ссылаться** | Весь файл. Режим B читает его перед сборкой |
| Взято дословно | Правило раскладки: `plugin.json` **только** в `.claude-plugin/`, всё остальное в корне плагина. Названо самым частым структурным провалом — в режиме B это первый чек |
| Взято дословно | Минимальный манифест и требование относительных путей с `./` |
| Взято дословно | `claude plugin validate <path>` как обязательная команда проверки режима B |
| Переписано | Таблица четырёх сущностей (skill / agent / command / plugin) → сведена к одному следствию: **все девять компонентов Dev Agent обязаны быть скиллами, а не агентами**, потому что они делят состояние через `.dev-agent/`. Это прямое применение правила «стадии, делящие состояние, должны быть скиллами» |
| Отброшено | Раздел про Codex и симлинки — вне скоупа |
| Отброшено | Marketplace-путь публикации — Dev Agent внутренний, ставится из репозитория |

## 6. `~/.claude/skills/writing-great-skills/SKILL.md`

Что делает скилл хорошим. **Самый плотный донор — из него взято больше всего.**

| Решение | Что именно |
|---|---|
| Взято дословно | **Предсказуемость как корневая добродетель**: один и тот же *процесс* каждый прогон, а не один и тот же вывод. Это ведущее слово всего `skill-forge` |
| Взято дословно | Информационная лестница: шаг в `SKILL.md` → reference в `SKILL.md` → внешний reference. Основа `platform-split.md` и `quality-rules.md` |
| Взято дословно | Шесть режимов отказа: **premature completion, duplication, sediment, sprawl, no-op, negation**. Целиком в `quality-rules.md` как диагностический чек-лист |
| Взято дословно | **Negation**: «не думай о слоне» делает слона доступнее. Правило: формулировать целевое поведение, а не запрет; запрет оставлять только как жёсткий guardrail и всегда с заменой |
| Взято дословно | **No-op-тест**: меняет ли строка поведение против дефолта. Применяется к каждому собираемому скиллу |
| Взято дословно | **Ведущие слова** — механика и два примера (_tight_, _red_) |
| Переписано | Выбор model-invoked vs user-invoked → для Dev Agent решено заранее: восемь рабочих скиллов **model-invoked** (разработчик не должен помнить их имена), `skill-forge` **user-invoked** с `disable-model-invocation: true` (служебный, вызывается только руками и не тратит контекст) |
| Переписано | Два типа разреза (по инвокации / по последовательности) → у нас состав зафиксирован, поэтому разрез не решается заново. Но правило разреза по последовательности применяется **внутри** скилла: прятать пост-фазы, если агент рвётся к завершению |
| Отброшено | Роутер-скилл как лекарство от когнитивной нагрузки — восемь скиллов model-invoked, роутер не нужен |

## 7. `~/.claude/skills/skill-creator/SKILL.md`

Процедура создания скилла.

| Решение | Что именно |
|---|---|
| Взято дословно | Четыре вопроса Capture Intent: что скилл позволяет делать, когда срабатывает, какой формат вывода, нужны ли тест-кейсы |
| Взято дословно | Различение: скиллы с объективно проверяемым выводом выигрывают от тест-кейсов, скиллы с субъективным (стиль текста) — часто нет. Прямо относится к нашим девяти: `element-markup` и `screen-blueprint` проверяемы, `interface-copy` частично |
| Переписано | Цикл «черновик → тестовые промпты → оценка → переписать» → у нас это **фаза верификации покрытия** с обязательными прогонами, прописанными в каждом промпте 01–09. Итерация с пользователем заменена на прогон против списка use case ID |
| Отброшено | `eval-viewer/generate_review.py` и количественные бенчмарки — инфраструктура `skill-creator`, у нас её нет |
| Отброшено | Раздел «Communicating with the user» про уровень жаргона — наша аудитория известна: разработчики |
| Отброшено | Оптимизатор описаний как отдельный скрипт — заменено проверяемыми правилами `description` из донора №1 |

## Структурные примеры — прочитаны как образцы, текст не заимствован

| Пример | Что подтвердил |
|---|---|
| `~/.claude/skills/accessibility/` | Тело 450 строк + `references/WCAG.md` (191) + `references/A11Y-PATTERNS.md` (233). Тело держит структуру WCAG по принципам POUR, references — справочные детали. Образец того, как тяжёлая тема остаётся в бюджете. Взято как ориентир для `element-markup` и `screen-review` |
| `~/.claude/skills/deliver-edge-cases/` | Тело 76 строк: When to Use / **When NOT to Use** / Instructions / Output Format / Quality Checklist / Examples. Секция «When NOT to Use» отсылает к соседним скиллам — ровно то, что нужно девяти скиллам Dev Agent, чтобы не пересекаться. Плюс `references/TEMPLATE.md` для формата вывода и `evals/` для проверяемости. **Эта структура взята как каркас шаблона спецификации** |
| `~/.claude/skills/verification-before-completion/SKILL.md` | Образец скилла-гейта: Iron Law → Gate Function по шагам → таблица «claim → requires → not sufficient» → таблица рационализаций. Механика «на каждую отговорку заранее заготовлен ответ» взята в `quality-rules.md` для борьбы с premature completion |
