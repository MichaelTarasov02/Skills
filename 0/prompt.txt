# Find Skills

This skill helps you discover and install skills from the open agent skills ecosystem.

## When to Use This Skill

Use this skill when the user:

- Asks "how do I do X" where X might be a common task with an existing skill
- Says "find a skill for X" or "is there a skill for X"
- Asks "can you do X" where X is a specialized capability
- Expresses interest in extending agent capabilities
- Wants to search for tools, templates, or workflows
- Mentions they wish they had help with a specific domain (design, testing, deployment, etc.)

## What is the Skills CLI?

The Skills CLI (`npx skills`) is the package manager for the open agent skills ecosystem. Skills are modular packages that extend agent capabilities with specialized knowledge, workflows, and tools.

**Key commands:**

- `npx skills find [query] [--owner <owner>]` - Search for skills interactively or by keyword, optionally scoped to a GitHub owner
- `npx skills add <package>` - Install a skill from GitHub or other sources
- `npx skills check` - Check for skill updates
- `npx skills update` - Update all installed skills

**Browse skills at:** https://skills.sh/

## How to Help Users Find Skills

### Step 1: Understand What They Need

When a user asks for help with something, identify:

1. The domain (e.g., React, testing, design, deployment)
2. The specific task (e.g., writing tests, creating animations, reviewing PRs)
3. Whether this is a common enough task that a skill likely exists

### Step 2: Check the Leaderboard First

Before running a CLI search, check the [skills.sh leaderboard](https://skills.sh/) to see if a well-known skill already exists for the domain. The leaderboard ranks skills by total installs, surfacing the most popular and battle-tested options.

For example, top skills for web development include:
- `vercel-labs/agent-skills` — React, Next.js, web design (100K+ installs each)
- `anthropics/skills` — Frontend design, document processing (100K+ installs)

### Step 3: Search for Skills

If the leaderboard doesn't cover the user's need, run the find command:

```bash
npx skills find [query] [--owner <owner>]
```

For example:

- User asks "how do I make my React app faster?" → `npx skills find react performance`
- User asks "can you help me with PR reviews?" → `npx skills find pr review`
- User asks "I need to create a changelog" → `npx skills find changelog`

### Step 4: Verify Quality Before Recommending

**Do not recommend a skill based solely on search results.** Always verify:

1. **Install count** — Prefer skills with 1K+ installs. Be cautious with anything under 100.
2. **Source reputation** — Official sources (`vercel-labs`, `anthropics`, `microsoft`) are more trustworthy than unknown authors.
3. **GitHub stars** — Check the source repository. A skill from a repo with <100 stars should be treated with skepticism.

### Step 5: Present Options to the User

When you find relevant skills, present them to the user with:

1. The skill name and what it does
2. The install count and source
3. The install command they can run
4. A link to learn more at skills.sh

Example response:

```
I found a skill that might help! The "react-best-practices" skill provides
React and Next.js performance optimization guidelines from Vercel Engineering.
(185K installs)

To install it:
npx skills add vercel-labs/agent-skills@react-best-practices

Learn more: https://skills.sh/vercel-labs/agent-skills/react-best-practices
```

### Step 6: Offer to Install

If the user wants to proceed, you can install the skill for them:

```bash
npx skills add <owner/repo@skill> -g -y
```

The `-g` flag installs globally (user-level) and `-y` skips confirmation prompts.

1. **Use specific keywords**: "react testing" is better than just "testing"
2. **Try alternative terms**: If "deploy" doesn't work, try "deployment" or "ci-cd"
3. **Check popular sources**: Many skills come from `vercel-labs/agent-skills` or `ComposioHQ/awesome-claude-skills`

## When No Skills Are Found

If no relevant skills exist:

1. Acknowledge that no existing skill was found
2. Offer to help with the task directly using your general capabilities
3. Suggest the user could create their own skill with `npx skills init`

Example:

```
I searched for skills related to "xyz" but didn't find any matches.
I can still help you with this task directly! Would you like me to proceed?

If this is something you do often, you could create your own skill:
npx skills init my-xyz-skill
```

## Why This Prompt Exists (read before working)

Earlier runs of this prompt lost large parts of the editor's scripts. Every loss came from the same mistake: hitting a mechanic in the script that had no obvious engine equivalent, and silently degrading it to the nearest thing. Four specific failures, and the rules that now prevent them:

| Editor mechanic | Past failure | Rule now |
| --- | --- | --- |
| Every screen has a Player 1 and a Player 2 version | Rewrote screens into "neutral" text that reads for both | Author both versions and route them with `nextForA`/`nextForB` (see `Role Mirroring`) |

## Reading The Script

`Novels/Source/Spec 4/How to read Editor Novel.md` is authoritative. Summary of the notation you must honor:

- `[QUESTION X]` is **one screen**. Two kinds:
  - **Text screen** — narration and/or direct speech, no options. Ends with a single arrow: `→[QUESTION Y]`, `→[SCENARIO Y]`, or `→[THE END]`.
  - **Choice screen** — carries `[ANSWER X]` options, each with its own arrow.
- `[ANSWER X]` carries: the button label, the destination arrow, and optionally `[Sympathy: +X]` / `[Sympathy: -X]`, which moves the shared Sympathy scale.
- `[SCENARIO X]` is a set of screens. **All paths inside one `[SCENARIO]` eventually lead to the next `[SCENARIO]`.**
- A screen ending `→[SCENARIO Y]` sends the player to `[QUESTION 1]` of `[SCENARIO Y]` — **unless** `[SCENARIO Y]` opens with Sympathy requirements, in which case the player lands on the `[QUESTION X]` matching their score.
- `What will you choose?` = the screen is answered by **Player 1**. `What will she choose?` / `What will he choose?` = answered by **Player 2**. The waiting player still sees the screen, with non-clickable buttons and `[Name] makes a choice...`.
- `[Name]` is a placeholder for the partner's profile name and **stays literal in the emitted JSON**. Do not invent a character name and do not bake one in.

Local `[QUESTION X]` / `[ANSWER X]` numbering **resets inside each `[SCENARIO]`**. It is a human-readable layer only; engine IDs are globally unique snake_case.

If the script is looser than this (missing tags, prose paragraphs, missing arrows), normalize it into the same model and log every inference in the `Script Reconciliation Report`.

Derive the pairing from the script; never ask.

## Role Mirroring (the mechanic that was being lost)

The editor writes one text; the app must show **two versions**. Per the legend, the Player 2 version transforms:

- narration: `you` → `he` (verb gains `-s`); `your` → `his`; object `you` → `him`; `she` → `you` (verb loses `-s`); `her` → `your` / `you` by context; case preserved;
- an exception: `you` meaning **both of you** is never transformed — keep such shared actions unambiguous;
- direct speech: the **speaker labels swap** (`You:` ↔ `[Name]:`); the spoken words themselves never change;
- `[Name]` resolves to the partner's profile name on each player's screen.

**Engine realization.** The engine supports this beyond the prologue: `nextForA` / `nextForB` re-fork the two roles after **any** answer, and the branches reconverge at the next shared Choice (engine doc, Part IV, "Сквозные развилки"). Navigation priority is `isEnding` → `nextForA/nextForB` → `nextScenarioId` → `nextQuestionId`.

Therefore:

1. **Every run of Text screens between two shared Choices becomes a role pair.** Author the A-chain exactly as the editor wrote it, and the B-chain as the legend's transformation of the same screens. Chain each side with `nextQuestionId`; both sides end on the same next shared Choice.
2. **Enter each run** through `nextForA` / `nextForB` on the answer that precedes it. The opening run uses `introStartIdA` / `introStartIdB`.
3. **ID convention:** `q_<scene>_<n>_a` and `q_<scene>_<n>_b` for the two versions of one script screen. This makes the coverage audit mechanical.
4. If a Text run is genuinely identical for both roles (pure `Both of you` narration with no `you`/`she`), you may emit one shared screen. Justify each such merge in the coverage audit.

**Known engine limit — Choice screens cannot be mirrored.** A shared Choice is a single object with one `text` and one `answers` array, shown to both players; `answeredBy` decides who clicks and drives the `[Name] makes a choice...` affordance. So:
- write the Choice `text` so it reads correctly for both players (situational framing, no `you`/`she` asymmetry);
- keep the editor's answer labels verbatim; if a label only parses from one POV, keep the editor's wording and record it in the `Engine Gap Register`;
- never invent a second Choice screen to fake per-role text.

## Scenario Structure

**One engine `scenario` per script `[SCENARIO X]`.** Same order, same count. Do not merge acts, do not split them, do not renumber.

- `scenario.initialQuestionId` = the engine ID of that act's `[QUESTION 1]` (or, for a gated act, the band router — see below).
- A **Choice answer** ending `→[SCENARIO Y]` uses `nextScenarioId`.
- A **Text screen** ending `→[SCENARIO Y]` sets its `nextQuestionId` to the target scenario's entry question ID. Engine IDs are globally unique and connectivity validation requires only that the target exists.
- `activationConditions` stays `null`. Never use it to make required content reachable.

If a backend constraint later forbids cross-scenario `nextQuestionId` from a Text screen, the fallback is to give the *preceding* Choice an answer carrying `nextScenarioId` — never to merge two acts. Record any use of the fallback in the `Engine Gap Register`.

## Sympathy

The engine model: each Choice answer earns `sympathyWeights[answerType] × question.weight`; both players' points sum to one shared scale; the score normalizes to `round(earned / maxPossible × 100)`, 0..100.

Two consequences you must handle explicitly, not silently:

**1. There are no negative weights.** `sympathyWeights` values are non-negative, so the editor's `[Sympathy: -3]` cannot be emitted as a negative number. Preserve the editor's **ordering and relative distance**, not the literal integers:
- rank every answer on a question by the editor's delta;
- pick an `answerType` per answer so that `sympathyWeights[type] × weight` reproduces that ranking (warm deltas → `Romantic`/`Kind`/`Sensitive`; neutral → `Playful`/`Practical`/`Rational`; negative deltas → the cheapest types, `Reserved` being the floor);
- an answer the editor scored negative must end up **strictly below** every non-negative answer on the same question.
- Publish the full mapping in the `Sympathy Balance Map`: script delta → chosen type → emitted points.

**2. Thresholds must be rescaled.** The editor writes raw thresholds (`>0`, `[-4;0]`, `<-4`). Compute the script's raw minimum and maximum across all complete paths, compute the engine's normalized min and max the same way, and map each raw boundary to its proportional position on 0..100. Show the arithmetic in `Sympathy Thresholds`. Verify every band is reachable by enumerating complete paths.

### Sympathy-Gated Entry

When `[SCENARIO Y]` opens with Sympathy requirements, the engine mechanism is `requiredSympathy` on answers (engine doc, Part VI): a variant unlocks only when the pair's current sympathy reaches the threshold, on the same 0..100 scale as `endings[]`.

Map it as follows:

- **Gated act reached from a Choice** — put the band routing on that Choice's answers: one answer per band, each routing to that band's entry question, each carrying the band's `requiredSympathy`. Keep at least one answer with no threshold (an engine rule: never lock a whole question).
- **Gated act that is the final act** — it is not a routing problem at all. Each band becomes an `endings[]` entry. See `Endings`.
- **Gated act reached from a Text screen, mid-story** — the engine has no automatic score-routed entry. Do not collapse the bands. Route the Text screen to the band entry that represents the editor's default (the middle band unless the script implies otherwise), keep every band's screens in the JSON, and record the whole thing in the `Engine Gap Register` as requiring native score-routed scenario entry. Never delete the unreachable bands; they are the spec for the backend work.

## Endings

An Interacta ending is a **screen without a choice** that tells where these two people go after the story. That is exactly `endings[]`: it is selected by the final sympathy score and rendered on the results screen.

Therefore:

- The script's `→[THE END]` narration **becomes `endings[]` content**, one entry per outcome band. Preserve the editor's ending prose as `endings[].text` (trim only for screen length; keep the wording).
- **Do not invent a terminal Choice screen.** The last Choice the editor actually wrote on each branch carries `isEnding: true` on its answers; that completes the session and the results screen shows the score-selected ending.
- Narration that sits between that last Choice and `→[THE END]` folds into the corresponding `endings[].text` rather than being dropped.
- `endings[]` holds 2–4 entries whose `[minSympathy, maxSympathy]` cover 0..100 with no gaps and no overlaps; stable unique `id`s; each with `title`, `text`, and `.../{slug}/ending-{id}.webp`.
- The editor's cold/low band stays as the editor wrote it. Do not convert it into a gentler ending.

## Localization

- en-US and ru-RU for every user-facing string, authored from the same beat.
- The A/B split is real screens, so **ru-RU mirroring is authored, not substituted** — write each role's Russian with correct gender agreement (past-tense verbs, adjectives, participles). This is why per-role screens matter more in Russian than in English.
- Identical across all JSON files: IDs, order, weights, answer types, routes, `answeredBy`, `nextForA`/`nextForB`, `requiredSympathy`, `sympathyWeights`, `endings` ids/ranges/imageUrls. Only user-facing strings differ, including `endings[].title`/`text`.
- `[Name]` stays literal in both locales.
- Author Russian; do not translate mechanically. False friends: restaurant `server` → `официант`/`официантка`, `check` → `счёт`, `reservation` → `бронь`, `date` → `свидание`.
- Never translate AnswerType enum values or convert IDs to Cyrillic.

## QA Before Finalizing

Structural:
- All three JSON files parse and validate against `Novels/Schemas/novel.schema.json`.
- `Technical Specification.json` is byte-identical to `Technical Specification.en-US.json`.
- Root emits `initialScenarioId`, `scenarios`, `genderA`/`genderB`, `introStartIdA`/`introStartIdB`, `sympathyWeights`, `endings`.
- Every `nextQuestionId` / `nextScenarioId` / `introStartId*` / `nextForA` / `nextForB` resolves to an existing ID.
- Every reachable branch terminates in `isEnding: true`; no dangling dead ends; no unreachable screens except those logged as `Emitted, unreachable`.
- Text: `type 0`, `weight 1`, `answers: []`. Choice: `type 1`, `nextQuestionId: null`, 2–3 answers.
- Every Choice keeps at least one answer without `requiredSympathy`.
- `endings[]` cover 0..100, no gaps, no overlaps.

Fidelity (the checks that matter most):
- **Coverage: 100%.** Every source `[QUESTION]` and `[ANSWER]` appears in the `Script Coverage Audit` with status `Carried`, `Mirrored pair`, `Merged (justified)`, or `Emitted, unreachable`. Any `Not carried` blocks delivery.
- **Counts reconcile:** source scenarios = engine scenarios; source choices = engine Choice screens; source answers = engine answers.
- **Order preserved:** scenario order and screen order match the script.
- **Mirroring complete:** every role-specific Text run has an A and a B version reachable via `introStartId*` or `nextForA`/`nextForB`.
- **Sympathy ordering preserved:** on every question, the emitted points rank the answers exactly as the editor's deltas did; negative-delta answers rank strictly lowest.
- **No invented content:** no screen, answer, scenario, or gate exists that is not in the script or listed in the gap-fill table.
- **Content preserved:** nothing softened or dropped for brand reasons; each risk appears in the `Content Risk Register`.

Product:
- Exactly one `Categories` list with 2 valid keys; one valid `Backend Category`; pairing/gender metadata only in `Specification.md`.
- Every `imageUrl` has a Visual Asset Brief row; `Cover Image URL` matches the header.
- `Database Insert.sql` matches the `novels` contract (en-US `content_json` as `::jsonb`, category JSON, 3–5 tags, `is_published false`, counters `0`/`0.0`, `NOW()`, `author_id NULL`).
- ru-RU is natural and structurally identical to en-US.
- Human-voice pass on authored copy only.

If any fidelity check fails, fix the JSON. Never fix it by editing the audit.
